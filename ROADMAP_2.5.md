# Roadmap 2.5

Цель ветки 2.5 — сделать распределённое нагрузочное тестирование устойчивым к рестартам,
упростить автоматизацию и добавить формальные критерии качества прогонов.

## M1 — Durable Coordinator

- Персистентный реестр Agent и management-state в PostgreSQL.
- Стабильная identity Agent после перезапуска Coordinator.
- Хранение только SHA-256 hash межсервисного токена Agent.
- Reconciliation состояния `BUSY` по telemetry активных run после рестарта.
- Flyway V25, интеграционные тесты и restart smoke.

## M2 — Единая модель запусков

- Общий жизненный цикл локальных и распределённых прогонов — реализован нормализованный runtime API.
- Персистентные assignments, статусы и причины остановки — реализовано для распределённых прогонов.
- Восстановление незавершённых запусков и явная reconciliation-политика — реализовано для Coordinator.
- Единые фильтры, история и повторный запуск в UI — реализованы для S3, ClickHouse и Kafka.

M2 завершён: `/api/runs` объединяет текущий жизненный цикл, а `/api/run-history` — долговременную
историю локальных и распределённых S3/ClickHouse/Kafka прогонов. Общая страница `/history`
поддерживает фильтры по контуру, типу, статусу, времени и текстовому запросу, дедуплицирует
агрегированные распределённые результаты и повторяет завершённый запуск из сохранённой конфигурации.
Локальная S3-история сохраняет фактический `stop_reason`; специализированные API и отчёты остаются
обратно совместимыми. Flyway V26 хранит назначения и прогресс распределённых запусков, а Coordinator
восстанавливает их после рестарта.

## M3 — API и автоматизация

- Версионированная OpenAPI-спецификация — реализован контракт Run API v1.
- CLI для профилей, запуска, ожидания результата и экспорта отчёта — реализован для S3, ClickHouse,
  Kafka и локального/распределённого scope.
- Идемпотентные команды — реализован персистентный `Idempotency-Key` для всех типов запуска.
- Стабильные machine-readable ошибки — реализованы для Run API v1, включая 401/403 и request ID.
- Контрактные тесты API и примеры для CI/CD — реализованы для Run API v1 и унифицированного экспорта.

M3 завершён: канонические маршруты `/api/v1/runs` и `/api/v1/run-history`
зафиксированы в OpenAPI 3.0.3. Старые адреса продолжают работать, а новый контракт использует
единый `application/problem+json`, постоянные коды ошибок и `X-Request-ID`. `evo-snt` выполняет
полный automation flow `profiles → start → wait → export` для S3, ClickHouse и Kafka в локальном и
распределённом scope; повтор команды безопасен благодаря персистентному отпечатку ключа, клиента и
нормализованного тела.

## M4 — Критерии производительности

- SLO gates по throughput, latency и error rate — реализованы политики с абсолютными override-порогами.
- Переиспользуемые workload profiles и наборы сценариев — добавлен общий каталог для трёх движков.
- Сравнение с baseline и формальный pass/fail результата — реализовано в API, CLI и reusable workflow.
- Расширенные resource limits — реализованы глобальные, engine/scope и per-run ограничения с UI и метриками.
- UI E2E — реализован отдельный Chromium workflow для общего каркаса, навигации, мониторинга,
  мобильного представления и legacy-redirect с сохранением screenshot/trace.
- Длительные проверки в эталонном окружении — реализованы повторяемые soak-окна, контроль drift,
  автономный systemd timer, локальный полный evidence и отдельная обезличенная сводка; для
  подключённых окружений сохранён ручной/reusable/opt-in scheduled workflow.

M4 завершён: зафиксированы OpenAPI 1.3, страница `/quality-gates`, CLI `evo-snt 0.5.0`, GitHub
Actions quality gate и автономный reference soak для изолированного контура. Длительная серия
применяет gate к каждому окну и сравнивает первую и последнюю треть по throughput, latency и error
rate; наружу может передаваться только сводка по белому списку. Подробности
эталонного запуска: [M4_SOAK_TESTS.md](M4_SOAK_TESTS.md). Политики и правила выбора baseline:
[M4_PERFORMANCE_GATES.md](M4_PERFORMANCE_GATES.md). Расширенные лимиты и правила эксплуатации:
[M4_RESOURCE_LIMITS.md](M4_RESOURCE_LIMITS.md). Браузерные E2E запускаются отдельным Maven-профилем
`browser-e2e` и workflow `Browser E2E`.

Каждый milestone выпускается через release candidate после зелёных unit, integration,
security и container smoke checks.
